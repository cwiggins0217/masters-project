# Objective

Evaluate how a selected configuration affects expected server operation
and a specific access method. This week's pilot examined disabling SSH
password authentication while preserving SSH key access.

The broader project asks whether selected CIS hardening recommendations
disrupt intended workloads and what measurable security benefit
accompanies those changes. This pilot establishes the testing method; it
does not establish full CIS compliance.

# Interpretation

Disabling SSH password authentication prevented the tested password-only
connection while preserving the tested key-only connection. The original
administrative workflow depended on passwords, so key enrollment was a
prerequisite for retaining remote access through this change. The
observed operational cost was a change in authentication workflow. Setup
time, support effort, application availability, and post-change
administrative capability have not yet been quantified. The security
conclusion is limited to the tested authentication method. No
brute-force campaign, CVE exploitation, compromise-rate measurement, or
complete attack chain was performed. Root access already failed before
the change, so that failure is not evidence of benefit from this
experiment. Keyboard-interactive authentication is a separate mechanism
that still needs checking.

# Remaining questions and next milestone

- Which exact CIS benchmark version, profile, and recommendation
  applies? Verify before labeling SSH-01 a CIS recommendation
  evaluation.
- Does any legitimate script or administrative process require password
  authentication?
- How much time did key enrollment and workflow migration require?
  Record future measurements rather than estimating missing past
  timings.
- Can the result be reproduced from the key-ready snapshot with the same
  account, client, packages, and network path?

Next milestone: repeat the baseline/post-change comparison from a known
snapshot, collecting the same tests and raw evidence in both conditions.
A later security scenario can explicitly assume an attacker has a valid
password but no authorized key; distinguish that scenario from password
guessing and from a general claim that the server cannot be compromised.

This week’s category is temporary-filesystem hardening, starting with
noexec on /tmp. It gives you a more substantial experiment: application
behavior, software maintenance, attacker execution, and whether a
workaround preserves the protection.
